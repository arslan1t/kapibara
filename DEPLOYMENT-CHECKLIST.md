# Развёртывание Капибары — пошаговый чеклист

Инструкция рассчитана на то, что вы делаете это впервые. Выполняйте разделы по
порядку: каждый следующий опирается на предыдущий.

**Никогда не вставляйте настоящие секреты в этот файл, в README или в код.**
Секреты живут только в переменных окружения вашей площадки и в локальном
`.env`, который не попадает в репозиторий.

Условные обозначения:

- 🔓 **публичное** значение — попадает в браузер, утечка не страшна;
- 🔒 **секрет** — только на сервере, никогда не в клиентском коде и не в git.

## 0. Что понадобится

| Сервис | Зачем | Обязателен на старте |
|---|---|---|
| Хостинг (Vercel / Railway / Render) | сам сайт | да |
| Домен | адрес магазина | да |
| PostgreSQL (Supabase / Neon / Railway) | все данные | да |
| Объектное хранилище (Supabase Storage / R2) | фотографии детей | да |
| Resend | письма | да |
| ЮKassa | онлайн-оплата | нет — можно стартовать с оплатой при подтверждении |
| Nano Banana | ИИ-иллюстрации | нет — можно готовить макеты вручную |

Заведите заранее: аккаунт хостинга, домен, аккаунт Supabase (или Neon + R2),
аккаунт Resend.

## 1. Хостинг и домен

**Рекомендация: Railway или Render.** Причина — этому проекту нужен постоянно
работающий фоновый воркер. На Vercel воркер живёт только как cron-функция с
лимитом времени выполнения (см. §9, вариант Б).

### 1.1 Создать проект

1. Подключите репозиторий к площадке.
2. Build command: `npm run build`
3. Start command: `npm start`
4. Node.js версии 20 или новее.
5. **Не запускайте деплой сейчас** — сначала переменные окружения (§10).

### 1.2 Домен

1. Добавьте домен в панели хостинга.
2. Пропишите DNS-записи, которые она покажет.
3. Дождитесь выпуска сертификата — HTTPS обязателен.

**Как проверить:** `https://ваш-домен` открывается, замок в адресной строке.

**Частые ошибки:** DNS ещё не разошёлся (подождите до часа); сертификат не
выпустился, потому что запись A/CNAME указывает не туда.

## 2. PostgreSQL

### 2.1 Создать базу

**Supabase:** Dashboard → New project → выберите регион ближе к покупателям →
задайте пароль базы (сохраните в менеджере паролей).

### 2.2 Скопировать две строки подключения

> ⚠️ **Не используйте строку вида `db.<ref>.supabase.co:5432`.**
> У новых проектов Supabase прямое подключение работает **только по IPv6**.
> Если у вашего интернет-провайдера, у ноутбука или у хостинга нет IPv6 — вы
> получите `Can't reach database server`, хотя пароль и адрес верны. Проверено
> на этом проекте: `db.yeqqhzobqmvhcpmypdhe.supabase.co` имеет только
> AAAA-запись, IPv4 у него нет.
>
> Берите **обе** строки у пулера (`...pooler.supabase.com`). Имя пользователя
> там другое — `postgres.<ref>`, а не просто `postgres`.

Project Settings → Database → Connection string:

| Что копировать | Порт | Куда | Тип |
|---|---|---|---|
| **Transaction** | 6543 | `DATABASE_URL` | 🔒 секрет |
| **Session** | 5432 | `DIRECT_URL` | 🔒 секрет |

К `DATABASE_URL` **допишите** `?pgbouncer=true`:

```
postgresql://postgres.xxx:ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:6543/postgres?pgbouncer=true
```

Без этого приложение упадёт с `prepared statement "s0" already exists`.

### 2.3 Применить миграции

Локально, с боевыми значениями в окружении:

```bash
DATABASE_URL="..." DIRECT_URL="..." npm run db:deploy
```

**Успешный вывод:**

```
4 migrations found in prisma/migrations
All migrations have been successfully applied.
```

### 2.4 Наполнить каталог (только при первом развёртывании)

```bash
DATABASE_URL="..." DIRECT_URL="..." npm run db:seed
```

**Успешный вывод:** `✔ Каталог: 2 товара, галерея: 6 изображений`

**Как проверить:** Supabase → Table editor → таблица `products` содержит две
строки.

**Частые ошибки:**

- `Can't reach database server` — чаще всего взята строка прямого подключения
  `db.<ref>.supabase.co` вместо пулера (см. предупреждение выше), реже —
  неверный пароль или база ещё создаётся.
- `prepared statement already exists` — забыли `?pgbouncer=true`.
- `advisory lock` при миграции — `DIRECT_URL` указывает на пулер, а не на порт
  5432.

**Откат:** `db:deploy` только добавляет и не удаляет данные. Если нужно
вернуться к предыдущей версии кода — разверните старый образ; схема совместима
с ним, пока вы не удаляли колонки вручную.

## 3. Хранилище файлов

Здесь лежат фотографии детей. Приватность бакета — не формальность.

**Рекомендация: Supabase Storage**, если база уже в Supabase: один аккаунт,
один счёт, ключ уже под рукой. Cloudflare R2 — если хотите дешёвый исходящий
трафик и вы готовы настроить два сервиса.

### 3.1 Вариант А — Supabase Storage

1. Storage → New bucket → имя `kapibara-private` → **«Public bucket» ВЫКЛЮЧЕН**.
2. Storage → New bucket → имя `kapibara-public` → «Public bucket» включён.
3. Project Settings → API → скопируйте **`service_role`** ключ.

> ⚠️ Нужен именно `service_role`. Ключи `anon` / `publishable`
> (`sb_publishable_...`) не подойдут: они предназначены для браузера и не могут
> ни писать в приватный бакет, ни выдавать подписанные ссылки.
>
> Это приложение **не обращается к Supabase из браузера вообще** — только с
> сервера. Поэтому переменных `NEXT_PUBLIC_SUPABASE_*` здесь нет и быть не
> должно: ключ, попавший в браузер, увидит любой посетитель.

| Переменная | Значение | Тип |
|---|---|---|
| `STORAGE_DRIVER` | `supabase` | 🔓 |
| `SUPABASE_URL` | `https://xxx.supabase.co` | 🔓 |
| `SUPABASE_SERVICE_ROLE_KEY` | ключ `service_role` | 🔒 |
| `SUPABASE_PRIVATE_BUCKET` | `kapibara-private` | 🔓 |
| `SUPABASE_PUBLIC_BUCKET` | `kapibara-public` | 🔓 |

**Проверка приватности (обязательно):** откройте в браузере
`https://xxx.supabase.co/storage/v1/object/public/kapibara-private/test.jpg`.
Должна быть ошибка доступа, а не файл. Если файл отдаётся — бакет публичный,
**исправьте прежде чем запускать сайт**.

### 3.2 Вариант Б — Cloudflare R2

1. R2 → Create bucket → `kapibara-private` (публичный доступ НЕ включать).
2. R2 → Create bucket → `kapibara-public`.
3. Manage R2 API Tokens → Create token → Object Read & Write, только на эти два
   бакета.

| Переменная | Значение | Тип |
|---|---|---|
| `STORAGE_DRIVER` | `s3` | 🔓 |
| `S3_ACCESS_KEY_ID` | из токена | 🔒 |
| `S3_SECRET_ACCESS_KEY` | из токена | 🔒 |
| `S3_REGION` | `auto` | 🔓 |
| `S3_ENDPOINT` | `https://<account>.r2.cloudflarestorage.com` | 🔓 |
| `S3_FORCE_PATH_STYLE` | `true` | 🔓 |
| `S3_PRIVATE_BUCKET` | `kapibara-private` | 🔓 |
| `S3_PUBLIC_BUCKET` | `kapibara-public` | 🔓 |

**Как проверить (оба варианта):** после деплоя `GET /api/health` должен
показать `"storage": { "ok": true, "durable": true }`.

**Частые ошибки:** `STORAGE_DRIVER=local` в production — приложение вернёт 503,
а воркер откажется стартовать (так и задумано: файлы исчезали бы при деплое).

## 4. Resend (письма)

### 4.1 Домен

1. resend.com → зарегистрируйтесь.
2. Domains → Add Domain → введите ваш домен.
3. Resend покажет DNS-записи. Добавьте **все**:
   - `MX` для поддомена отправки;
   - `TXT` SPF;
   - `TXT` DKIM (обычно две-три записи).
4. Нажмите Verify. Обычно занимает от минут до часа.

**Не переходите дальше, пока домен не в статусе Verified** — Resend отклонит
отправку с неподтверждённого домена.

#### Если домена ещё нет

Resend разрешает отправку с адреса `onboarding@resend.dev`, но **только на почту
владельца аккаунта**. Этого хватает, чтобы проверить, что ключ и код работают:

```
MAIL_FROM="Капибара <onboarding@resend.dev>"
```

Чего так делать **нельзя**: принимать заказы. Письма о регистрации,
восстановлении пароля и заказах не дойдут ни до кого, кроме вас — покупатель
не сможет ни подтвердить адрес, ни восстановить пароль. Для магазина нужен
подтверждённый домен.

### 4.2 Ключ

API Keys → Create API Key → права **Sending access** (не Full access).

Ключ только на отправку — правильный выбор. `/api/health` это учитывает и
считает такой ключ исправным, хотя список доменов ему читать не разрешено.

| Переменная | Значение | Тип |
|---|---|---|
| `MAIL_DRIVER` | `resend` | 🔓 |
| `RESEND_API_KEY` | `re_...` | 🔒 |
| `MAIL_FROM` | `Капибара <no-reply@ваш-домен>` | 🔓 |
| `MAIL_REPLY_TO` | `support@ваш-домен` (необязательно) | 🔓 |

**Как проверить:** `GET /api/health` → `"mail": { "ok": true, "driver": "resend" }`.
Затем зарегистрируйте тестовый аккаунт и дождитесь письма (§ LIVE-VERIFICATION).

**Частые ошибки:** домен в `MAIL_FROM` не совпадает с подтверждённым;
использован ключ с правами только на чтение.

## 5. ЮKassa (онлайн-оплата)

Можно пропустить на старте — тогда магазин работает с оплатой при
подтверждении и **нигде не утверждает, что деньги получены**.

### 5.1 Учётные данные

Личный кабинет ЮKassa → Настройки → Магазин:

| Переменная | Где взять | Тип |
|---|---|---|
| `YOOKASSA_SHOP_ID` | «shopId» | 🔒 |
| `YOOKASSA_SECRET_KEY` | «Секретный ключ» | 🔒 |
| `YOOKASSA_WEBHOOK_SECRET` | придумайте: `openssl rand -hex 32` | 🔒 |

### 5.2 Return URL

Задаётся приложением автоматически:

```
https://ВАШ-ДОМЕН/order-success?order=<id заказа>
```

Отдельно настраивать не нужно — важно лишь, чтобы `NEXT_PUBLIC_SITE_URL` был
боевым доменом.

### 5.3 Webhook URL

Настройки → **Уведомления** → HTTP-уведомления:

```
https://ВАШ-ДОМЕН/api/payments/webhook/yookassa
```

События (отметить все три):

- `payment.succeeded`
- `payment.canceled`
- `payment.waiting_for_capture`

Если задан `YOOKASSA_WEBHOOK_SECRET`, добавьте заголовок
`x-webhook-secret: <это значение>`. Запрос без него отклоняется.

### 5.4 Тестовый режим

1. В ЮKassa включите тестовый магазин и возьмите **тестовые** shopId и ключ.
2. Разверните их на staging-окружении, не на боевом.
3. Оформите заказ и оплатите тестовой картой из документации ЮKassa.

### 5.5 Проверка платежом на минимальную сумму

На боевых ключах, перед открытием магазина:

1. В админке временно поставьте цену книги **1 ₽**.
2. Оформите заказ со своей настоящей картой.
3. Оплатите.
4. **Верните настоящую цену немедленно.**

**Что должно появиться в базе:**

| Таблица | Ожидание |
|---|---|
| `orders` | новая строка, `paymentStatus = 'paid'`, `orderStatus = 'in_progress'` |
| `payments` | строка `provider='yookassa'`, `status='succeeded'`, заполнен `paidAt`, `amount = 1` |
| `order_status_history` | запись «Оплата подтверждена провайдером» |

**Признаки успеха:** страница `/order-success` показывает «Оплата получена».

**Признаки провала:**

- заказ остался `unpaid` → вебхук не доходит: проверьте URL, заголовок секрета
  и что домен доступен снаружи;
- `payments.status='failed'` и `failureReason` про несовпадение суммы → в
  ЮKassa настроена другая валюта или сумма изменилась между созданием и
  оплатой.

**Откат:** уберите переменные ЮKassa и передеплойте — магазин вернётся к оплате
при подтверждении, уже созданные заказы останутся.

## 6. Nano Banana (ИИ-иллюстрации)

**Интеграция не проверена с настоящим API.** Клиент написан по типовой схеме
(отправка → опрос → скачивание). Пока ключа нет, сайт честно пишет, что
иллюстрации готовятся вручную.

| Переменная | Значение | Тип |
|---|---|---|
| `NANO_BANANA_API_KEY` | ключ провайдера | 🔒 |
| `NANO_BANANA_API_URL` | если отличается от значения по умолчанию | 🔓 |
| `NANO_BANANA_STYLE_ID` | если согласован пресет | 🔓 |

**Перед включением на боевом сайте** сверьте с документацией провайдера и при
необходимости поправьте **только** `src/lib/generation/nano-banana.ts`:

| Что | Где в файле | Сейчас предполагается |
|---|---|---|
| Заголовок авторизации | `generate`, `checkJob` | `Authorization: Bearer <key>` |
| Поля запроса | `generate` | `photo`, `child_name`, `book`, `pages`, `style_id` |
| Идентификатор задания | `ProviderJobResponse.id` | `id` |
| Статусы | `mapStatus` | `queued`/`processing`/`running`/`completed`/`succeeded`/`cancelled` |
| Результаты | `downloadImages` | `images[].url`, `images[].page` |

Контрактный тест на локальном mock-сервере: `tests/nano-banana.test.ts` —
он фиксирует ожидаемую форму запроса и ответа, чтобы расхождение с реальным API
обнаружилось сразу.

## 7. Фоновый воркер

Генерация иллюстраций занимает минуты и **не** выполняется внутри запроса.
Нужен один из двух вариантов.

### Вариант А — отдельный процесс (рекомендуется)

На Railway/Render создайте **второй сервис из того же репозитория**:

- Build command: `npm run build`
- Start command: `npm run worker`
- Те же переменные окружения, что и у сайта.

**Успешный вывод в логах:**

```
{"level":"info","event":"worker.started",...}
{"level":"info","event":"worker.tick","claimed":0,...}
```

Можно запускать несколько экземпляров — задания захватываются условным UPDATE,
одно задание двум воркерам не достанется.

### Вариант Б — cron (Vercel и другие serverless)

1. Задайте `CRON_SECRET` (🔒): `openssl rand -hex 32`.
2. Добавьте в `vercel.json`:

```json
{ "crons": [{ "path": "/api/cron/worker", "schedule": "* * * * *" }] }
```

**Честное ограничение Vercel:** функция обрывается по таймауту плана (10 с на
Hobby, 60 с на Pro). Тик рассчитан на это — он берёт не более трёх заданий и
сам укладывается в бюджет, а недоделанное подхватит следующий запуск. Но если
провайдер отвечает медленно, отставание будет расти. **Для стабильной работы
генерации выбирайте вариант А.**

**Как проверить:**

```bash
curl -H "x-cron-secret: ВАШ_СЕКРЕТ" https://ВАШ-ДОМЕН/api/cron/worker
```

Ожидаемо: `{"ok":true,"claimed":0,...}`. Без секрета — `404`.

## 8. Первый администратор

Публичной регистрации администратора нет и быть не должно.

```bash
DATABASE_URL="..." DIRECT_URL="..." \
  npm run admin:create -- admin@ваш-домен "Имя Фамилия" "СильныйПароль1"
```

Пароль: минимум 8 символов, хотя бы одна буква и одна цифра. Сразу сохраните
его в менеджере паролей.

**Как проверить:** войдите на `https://ВАШ-ДОМЕН/login`, откройте `/admin` —
должна открыться панель. Обычный покупатель на `/admin` видит «Нет доступа».

## 9. Переменные окружения — полный список

Занесите в панель хостинга. Полный справочник с комментариями — `.env.example`.

### Обязательные

| Переменная | Тип | Примечание |
|---|---|---|
| `DATABASE_URL` | 🔒 | пулер + `?pgbouncer=true` |
| `DIRECT_URL` | 🔒 | прямое подключение, порт 5432 |
| `AUTH_SECRET` | 🔒 | `openssl rand -base64 32` |
| `AUTH_URL` | 🔓 | `https://ВАШ-ДОМЕН` |
| `NEXT_PUBLIC_SITE_URL` | 🔓 | `https://ВАШ-ДОМЕН` |
| `STORAGE_DRIVER` | 🔓 | `supabase` или `s3` |
| + переменные хранилища из §3 | | |
| `MAIL_DRIVER`, `RESEND_API_KEY`, `MAIL_FROM` | 🔒/🔓 | §4 |

### По необходимости

| Переменная | Когда нужна |
|---|---|
| `CRON_SECRET` | только при варианте Б в §7 |
| `YOOKASSA_*` | онлайн-оплата |
| `NANO_BANANA_*` | ИИ-иллюстрации |
| `TRUSTED_PROXY_COUNT` | только если у вас свои прокси перед площадкой |
| `LOG_LEVEL` | по умолчанию `info` |

**Важно:** менять `AUTH_SECRET` после запуска — значит разлогинить всех.

## 10. Финальный деплой

```bash
npm ci
npm run typecheck
npm run lint
npm test                 # требует локальный PostgreSQL: npm run db:local
npm run build
npm run check:secrets
```

Все шесть должны пройти. Затем задеплойте на площадке.

**Проверка сразу после деплоя:**

```bash
curl https://ВАШ-ДОМЕН/api/health
```

Ожидаемо: HTTP 200 и

```json
{
  "status": "ok",
  "checks": {
    "database": { "ok": true },
    "storage": { "ok": true, "durable": true },
    "mail": { "ok": true, "driver": "resend" }
  }
}
```

Если `503` — смотрите, какая проверка `false`, и вернитесь к её разделу.

Далее пройдите **LIVE-VERIFICATION-CHECKLIST.md** целиком.

## 11. Откат

| Ситуация | Действие |
|---|---|
| Плохой релиз | верните предыдущий деплой в панели хостинга; схема БД совместима |
| Сломалась миграция | `db:deploy` применяет по одной и останавливается на ошибке; исправьте SQL и запустите снова — уже применённые не повторяются |
| Утёк `AUTH_SECRET` | сгенерируйте новый, передеплойте: все сессии завершатся, покупатели войдут заново |
| Утёк ключ хранилища | отзовите ключ у провайдера, создайте новый, обновите переменную, передеплойте |
| Утёк ключ ЮKassa | немедленно перевыпустите в кабинете ЮKassa и обновите переменную |
| Ошибочный платёж | статус меняется в админке вручную; **автоматического возврата нет**, возврат делается в кабинете ЮKassa |
| Нужно срочно отключить оплату | уберите `YOOKASSA_*` и передеплойте — вернётся оплата при подтверждении |
| Нужно срочно отключить генерацию | уберите `NANO_BANANA_API_KEY` и передеплойте |
