# Капибара

Интернет-магазин персонализированных детских книг: покупатель выбирает историю,
добавляет имя и фотографию ребёнка и оформляет заказ. Есть личный кабинет,
панель администратора и фоновая обработка задач.

---

## 1. Архитектура

| Слой | Решение |
|---|---|
| Фреймворк | Next.js 15 (App Router), React 19, TypeScript |
| Стили | Tailwind CSS 3, токены бренда в `globals.css` |
| База данных | PostgreSQL + Prisma ORM |
| Файлы | Supabase Storage или S3-совместимое хранилище |
| Почта | Resend (или SMTP) |
| Оплата | ЮKassa, с ручной оплатой как запасным вариантом |
| Иллюстрации | Nano Banana |
| Фоновые задачи | Очередь в БД + отдельный воркер или cron |
| Аутентификация | Auth.js v5, Credentials, JWT в httpOnly-cookie |
| Пароли | bcrypt, 12 раундов |

## 2. База данных

16 таблиц: `users`, `consents`, `verification_tokens`, `products`,
`product_images`, `product_variants`, `orders`, `order_items`,
`personalizations`, `order_status_history`, `payments`, `reviews`,
`generation_jobs`, `generation_results`, `email_messages`,
`rate_limit_counters`.

Особенности:

- **Деньги — целые числа** (рубли), без плавающей точки.
- **Снимок цены в заказе.** `order_items` хранит название и цену на момент
  покупки, поэтому изменение товара не меняет старые заказы.
- **CHECK-ограничения** на все статусы, суммы и оценки: недопустимое состояние
  невозможно записать даже вручную через консоль. См. миграцию
  `20260805000100_integrity_constraints`.
- **`total = subtotal + deliveryPrice`** и **`lineTotal = unitPrice × quantity`**
  проверяются базой, а не только приложением.
- **Номер заказа выдаёт последовательность PostgreSQL** — два одновременных
  оформления не могут получить один номер.
- **Согласия хранятся отдельно** — тип, факт принятия, время и версия документа.
- **Отзыв привязан к позиции заказа** (`orderItemId` уникален): отзыв может
  существовать только у того, кто действительно получил книгу.
- **Токены писем хранятся хешем** — утечка базы не даёт рабочих ссылок.
- **Аренда заданий** (`lockedAt`/`lockedBy`) — два воркера не возьмут одно
  задание, а задание умершего воркера подхватывается после истечения аренды.

## 3. Локальный запуск

PostgreSQL ставить не нужно: `npm run db:local` поднимает настоящий PostgreSQL
(сборка PGlite в WebAssembly) на порту 55432.

```bash
npm install
cp .env.example .env          # заполнить AUTH_SECRET
npm run db:local &            # PostgreSQL для разработки
npm run db:deploy             # применить миграции
npm run db:seed               # наполнить каталог
npm run dev
```

Для локальной разработки в `.env` достаточно:

```
DATABASE_URL="postgresql://postgres:postgres@127.0.0.1:55432/postgres?pgbouncer=true&connection_limit=1"
DIRECT_URL="postgresql://postgres:postgres@127.0.0.1:55432/postgres"
AUTH_SECRET="<openssl rand -base64 32>"
AUTH_URL="http://localhost:3000"
NEXT_PUBLIC_SITE_URL="http://localhost:3000"
STORAGE_DRIVER="local"
```

## 4. Первый администратор

Публичной регистрации администратора нет и не должно быть. Роль хранится в базе
и недоступна для изменения из браузера; CHECK-ограничение допускает только
значения `customer` и `admin`.

```bash
npm run admin:create -- admin@example.com "Имя Фамилия" "СильныйПароль1"
```

Если аккаунт с таким адресом уже существует, он повышается до администратора
(пароль при этом не меняется). Требования к паролю: не менее 8 символов,
минимум одна буква и одна цифра.

Смена пароля — отдельное явное действие:

```bash
npm run admin:create -- admin@example.com --reset-password
```

Пароль будет запрошен в терминале, поэтому не попадёт в историю команд. Смена
пароля обнуляет все выданные ранее сессии этой учётной записи: обычная причина
сбросить пароль администратора — подозрение, что старый известен кому-то ещё.

В production запускайте команду там, где доступен `DATABASE_URL` — например,
`railway run npm run admin:create -- …` или через консоль хостинга. Панель
доступна на `/admin`; покупатель, открывший этот адрес, получает страницу
«Нет доступа».

## 5. Развёртывание

### 5.1 PostgreSQL

Подойдёт любой управляемый PostgreSQL 14+ (Supabase, Neon, Railway, RDS).

1. Создайте базу и получите две строки подключения:
   - **пулер** (транзакционный режим) → `DATABASE_URL`;
   - **прямое подключение** → `DIRECT_URL`.
2. Если `DATABASE_URL` указывает на пулер в transaction mode, добавьте
   `?pgbouncer=true`. Без этого Prisma получит ошибку
   `prepared statement "s0" already exists`.
3. Применяйте миграции **до** запуска нового кода:

```bash
npm run db:deploy
npm run db:seed        # только при первом развёртывании
```

`db:deploy` не удаляет данные и безопасен для повторного запуска.

**Supabase:** Project Settings → Database → Connection string. «Transaction»
(порт 6543) → `DATABASE_URL`, «Session» (порт 5432) → `DIRECT_URL`.

### 5.2 Хранилище файлов

Фотографии детей и сгенерированные иллюстрации хранятся в **приватном** бакете
и отдаются только по подписанным ссылкам на 5 минут после проверки прав.
Артворк каталога — в публичном.

**Вариант А — Supabase Storage**

1. Storage → New bucket → `kapibara-private`, **«Public bucket» выключен**.
2. Storage → New bucket → `kapibara-public`, «Public bucket» включён.
3. Project Settings → API → скопируйте `service_role` ключ.
4. Переменные:

```
STORAGE_DRIVER="supabase"
SUPABASE_URL="https://PROJECT.supabase.co"
SUPABASE_SERVICE_ROLE_KEY="…"
SUPABASE_PRIVATE_BUCKET="kapibara-private"
SUPABASE_PUBLIC_BUCKET="kapibara-public"
```

**Вариант Б — S3-совместимое хранилище**

1. Создайте два бакета. У приватного включите Block Public Access.
2. Создайте ключ с правами `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`
   на оба бакета — и ни на что больше.
3. Переменные:

```
STORAGE_DRIVER="s3"
S3_ACCESS_KEY_ID="…"
S3_SECRET_ACCESS_KEY="…"
S3_REGION="auto"
S3_PRIVATE_BUCKET="kapibara-private"
S3_PUBLIC_BUCKET="kapibara-public"
S3_ENDPOINT="https://ACCOUNT.r2.cloudflarestorage.com"   # для R2/MinIO/Yandex
S3_FORCE_PATH_STYLE="true"
```

Проверьте после развёртывания: `/api/health` должен показать
`"storage": { "ok": true, "durable": true }`. С `STORAGE_DRIVER=local`
приложение в production вернёт 503, а воркер откажется стартовать.

### 5.3 Почта (Resend)

1. resend.com → Domains → добавьте домен и внесите записи DKIM/SPF.
2. API Keys → создайте ключ с правом только на отправку.
3. Переменные:

```
MAIL_DRIVER="resend"
RESEND_API_KEY="re_…"
MAIL_FROM="Капибара <no-reply@ваш-домен>"
MAIL_REPLY_TO="support@ваш-домен"     # необязательно
```

Домен в `MAIL_FROM` обязан быть подтверждён, иначе Resend отклонит отправку.
Подключены письма: подтверждение адреса, повторная отправка подтверждения,
восстановление пароля, подтверждение заказа, смена статуса заказа.

Проверка: `/api/health` → `"mail": { "ok": true, "driver": "resend" }`.

### 5.4 Оплата (ЮKassa)

1. Личный кабинет ЮKassa → Настройки → Магазин: `shopId` и секретный ключ.
2. Сгенерируйте свой секрет вебхука: `openssl rand -hex 32`.
3. Переменные:

```
YOOKASSA_SHOP_ID="…"
YOOKASSA_SECRET_KEY="…"
YOOKASSA_WEBHOOK_SECRET="…"
```

4. **Вебхук.** Зарегистрируйте в ЮKassa (Настройки → Уведомления) адрес:

```
https://ВАШ-ДОМЕН/api/payments/webhook/yookassa
```

События: `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`.

Если задан `YOOKASSA_WEBHOOK_SECRET`, добавьте к уведомлению заголовок
`x-webhook-secret` с этим значением — запрос без него будет отклонён.

**Как защищён вебхук:**

- тело запроса используется только чтобы узнать, *какой* платёж изменился;
  статус перечитывается из API ЮKassa, поэтому подделанный запрос не может
  пометить заказ оплаченным;
- сумма из события сверяется с суммой заказа — при расхождении платёж
  помечается ошибочным и заказ не оплачивается;
- повторная доставка того же события ничего не меняет;
- при потере вебхука фоновый воркер сам перечитывает статус (раздел 5.6).

Без этих переменных магазин работает с оплатой при подтверждении и **нигде не
утверждает, что деньги получены**.

### 5.5 Иллюстрации (Nano Banana)

```
NANO_BANANA_API_KEY="…"
NANO_BANANA_API_URL="https://api.nanobanana.ai/v1"   # если отличается
NANO_BANANA_STYLE_ID="…"                             # если согласован пресет
```

Что уже реализовано: проверка формата и размера файла по сигнатуре, таймауты
(60 с на постановку, 30 с на опрос и загрузку), обработка отменённых и
провалившихся заданий, ограничение числа попыток, сохранение статуса в БД,
запись результатов в приватное хранилище.

### 5.6 Фоновый воркер

Генерация иллюстраций занимает минуты, поэтому она **не** выполняется в
запросе — задание кладётся в очередь в БД. Покупатель может закрыть страницу.
Выберите один из двух вариантов.

**Вариант А — отдельный процесс** (Railway, Render, Fly, контейнер, systemd):

```bash
npm run worker
```

Тот же образ, что и у сайта, другая команда запуска. Можно запускать несколько
экземпляров: задания захватываются условным UPDATE, поэтому одно задание не
попадёт двум воркерам. Воркер корректно завершает работу по SIGTERM.

**Вариант Б — cron** (Vercel и другие serverless-платформы):

```
CRON_SECRET="<openssl rand -hex 32>"
```

Вызывайте по расписанию, раз в минуту:

```
GET https://ВАШ-ДОМЕН/api/cron/worker
Authorization: Bearer $CRON_SECRET
```

Для Vercel добавьте в `vercel.json`:

```json
{ "crons": [{ "path": "/api/cron/worker", "schedule": "* * * * *" }] }
```

Vercel Cron сам передаёт `Authorization: Bearer $CRON_SECRET`.

Без `CRON_SECRET` эндпоинт отвечает 404 на любой запрос.

Обе схемы выполняют один и тот же код: берут задания из очереди, опрашивают
провайдера, перечитывают «зависшие» платежи, удаляют истёкшие токены и счётчики
лимитов.

### 5.7 Сборка и проверка

```bash
npm ci
npm run db:deploy
npm run build
npm run check:secrets     # падает, если секрет попал в клиентский бандл
npm start
```

Health-check: `GET /api/health` — 200, когда приложение готово обслуживать
покупателей, 503 при недоступной базе или ненадёжном хранилище. Секретов,
хостов и имён бакетов не отдаёт.

## 6. Что работает

**Покупатель**
- Регистрация по email с валидацией на клиенте и на сервере.
- Три обязательных согласия; каждое сохраняется с версией документа и временем.
- Подтверждение адреса по ссылке из письма, повторная отправка из кабинета.
- Восстановление пароля: одноразовая ссылка на час. Ответ формы одинаков вне
  зависимости от того, зарегистрирован адрес или нет.
- Вход, выход, защищённые маршруты.
- Личный кабинет: обзор, профиль, смена пароля, заказы, карточка заказа.
- Каталог, главная и футер читают товары из базы; снятый с продажи товар
  исчезает из каталога, а его страница отдаёт 404.
- Персонализация: имя только кириллицей, загрузка фотографии в приватное
  хранилище с проверкой по сигнатуре файла.
- Корзина и оформление заказа с созданием реальной записи и платежа.
- Отзыв о доставленном заказе — с проверкой, что заказ действительно ваш.

**Администратор**
- Сводка по реальным данным; выручка — только по оплаченным заказам.
- Заказы: поиск, фильтры, карточка, смена статуса и оплаты, комментарий,
  история изменений, платежи и повторная сверка с провайдером.
- Товары: создание, редактирование, публикация, «Скоро», архивирование.
- Галерея товара: загрузка, порядок, обложка, удаление файла вместе с записью.
- Отзывы: очередь модерации, одобрение, отклонение с причиной, закрепление.
- Клиенты: список с числом заказов и суммой.

**Безопасность**
- Роль читается из базы при каждом обращении, а не берётся из токена.
- Цены считаются на сервере; данные из браузера не используются.
- Сумма платежа сверяется с заказом; повторный вебхук ничего не меняет.
- Заказы, фотографии и сгенерированные иллюстрации читаются только владельцем
  или администратором; посторонний получает 404, а не 403.
- Приватные файлы отдаются по подписанным ссылкам на 5 минут.
- Токены писем хранятся хешем, действуют один раз и имеют срок.
- Ограничение частоты: вход, регистрация, восстановление пароля, отзывы,
  загрузки, оформление заказа — в базе, а не в памяти процесса.
- Логи маскируют пароли, токены, заголовки авторизации, ключи файлов,
  платёжные секреты и персональные данные, включая адреса получателей писем
  (`arslan@example.com` → `a***@example.com`).
- Сборка проверяется на попадание серверных секретов в клиентский бандл.

## 6a. Развёртывание на Beget

Боевой хостинг — Beget, `https://capibara.su`. Приложение работает под
Apache mod_passenger: Passenger сам запускает процесс и поднимает его после
перезагрузки. Разворачивает один скрипт:

```bash
ENV_FILE=~/kapibara-production.env ./scripts/deploy-beget.sh
```

Три вещи, которые здесь неочевидны и стоили отладки:

1. **Приложение обязано лежать внутри каталога сайта** (`~/capibara/app`), а не
   рядом с ним. Apache обслуживает сайт от отдельной учётной записи
   (`sshipuf9__capibara__ae`); Beget выдаёт каталогу сайта default-ACL на неё, и
   всё созданное внутри наследует доступ. Снаружи доступа нет, а `setfacl`
   клиенту запрещён — приложение в `~/kapibara` даёт 403, который не лечится
   правами.

2. **Node тоже живёт в дереве сайта.** Passenger запускает его от той же
   учётной записи, а бинарник под `~/.local` (700, без ACL) ей недоступен.
   `~/.local/node` — симлинк на копию в дереве сайта.

3. **`.env` читает `passenger-entry.js`**, а не оболочка. Passenger стартует
   процесс сам, sourc'ить `.env` некому, а standalone-сервер Next его не
   читает. Секреты остаются в файле с правами 600 вне DocumentRoot — в
   `.htaccess` через `PassengerEnvVar` их класть нельзя, это файл внутри
   веб-дерева.

Перезапуск — `touch tmp/restart.txt` в корне проекта; скрипт делает это сам.

### Режим обслуживания

Закрывает `capibara.su` и оставляет сайт работающим на `www.capibara.su`:

```bash
MAINTENANCE=1 ./scripts/deploy-beget.sh   # закрыть
MAINTENANCE=0 ./scripts/deploy-beget.sh   # открыть обратно
```

Режим **липкий**: если он включён, обычный деплой его сохраняет. Открыть
магазин публике — отдельное решение, а не побочный эффект выкатки.

Основной домен отвечает 503 со страницей `public/maintenance.html`, а не 404
и не 200: это временный код, поисковики сохраняют страницы в индексе.

Заголовок `Vary: Host` обязателен. Один путь отдаёт разное на двух именах, и
без него промежуточный кэш считает их одним ресурсом — наблюдалось, как
закэшированная заглушка с основного домена доставалась посетителям поддомена.

## 7. Тесты

```bash
npm run db:local &
npm run db:deploy
npm test
npm run db:seed        # тесты очищают базу — верните каталог
```

**Тесты очищают все таблицы** (`TRUNCATE … CASCADE`), поэтому после прогона
запустите `npm run db:seed`.

Набор **отказывается запускаться**, если `DATABASE_URL` указывает не на
localhost — предупреждения в документации недостаточно, когда одна команда
способна стереть боевой магазин. Для одноразовой базы в CI есть явный
обходной путь:

```bash
ALLOW_DESTRUCTIVE_TESTS=yes-i-am-sure npm test
```

Ставьте его только там, где потеря всех данных допустима.

92 теста на настоящем PostgreSQL: аутентификация и токены, ограничение частоты,
разграничение доступа между покупателями, ценообразование и ограничения БД,

## 8. Не реализовано

| Функция | Состояние |
|---|---|
| Возврат платежа из панели | Статус «Возврат» проставляется вручную; обращения к API провайдера на возврат нет. |
| Гостевой отзыв | Заказ можно оформить без входа, но отзыв и история доступны только зарегистрированным. |
| Удаление аккаунта покупателем | Не реализовано; удаление по запросу выполняется администратором в базе. |
| Автоудаление фотографий после печати | Срок хранения не реализован. Не обещайте покупателям автоматическое удаление, пока это не сделано. |
| Метрики и трассировка | Есть структурные логи и `/api/health`; экспорта в Prometheus/OpenTelemetry нет. |
