# Production readiness — Капибара

Итог независимого предрелизного аудита. Проверялось само приложение, а не
предыдущие отчёты.

Среда проверки: PostgreSQL 18.3, Node 26.5, Next.js 15.5.22, Prisma 6.19.3.
Дата: 5 августа 2026.

---

## 1. Executive Summary

**Готов к настройке развёртывания (Ready for deployment configuration).**

Код-уровневых блокеров не осталось. Аудит нашёл и исправил девять реальных
дефектов, включая утечку персональных данных покупателя через страницу
подтверждения заказа, доступ посторонних к иллюстрациям ребёнка, публичную
точку рассылки писем и критический RCE в устаревшей версии Next.js. Все исправления закрыты
регрессионными тестами; 90 тестов проходят на настоящем PostgreSQL.

Публичный запуск **пока невозможен** по одной причине: ни одна внешняя
интеграция (Resend, ЮKassa, Nano Banana, объектное хранилище) не проверялась с
настоящими учётными данными — их не было в среде разработки. Код написан
полностью, но до первого успешного обмена с каждым сервисом считать их
работающими нельзя.

Отдельно: клиент Nano Banana написан **без подтверждённой документации API**.
Это единственная интеграция, где расхождение с реальностью вероятно, а не
просто возможно.

## 3. Fixed During This Audit

Девять реальных дефектов. Косметика не включена.

### 3.1 IDOR на странице подтверждения заказа — Critical

- **Файлы:** `src/app/(main)/order-success/page.tsx`
- **Суть:** страница читала заказ по `?order=<id>` **без единой проверки прав** и
  показывала номер заказа, сумму и **адрес электронной почты покупателя**. Любой,
  кто получил или подобрал id заказа, читал чужие персональные данные. Тот же
  путь запускал сверку платежа для чужого заказа.
- **Исправление:** страница показывает данные только владельцу аккаунта либо
  предъявителю httpOnly-cookie, выданной в момент оформления
  (`src/lib/claim.ts`). Остальным — нейтральная страница без данных.
- **Проверка:** тест «an order id alone does not entitle a stranger to the
  order»; живой запрос на боевой сборке — email, номер и сумма отсутствуют в
  HTML.

### 3.2 Задания генерации без владельца читал кто угодно — High

- **Файлы:** `src/lib/generation/index.ts`, `src/app/api/generation/[jobId]/route.ts`,
  `src/app/api/uploads/[key]/route.ts`
- **Суть:** проверка была `if (job.userId && job.userId !== userId) return null`.
  У анонимного предпросмотра `userId` равен `null`, поэтому условие никогда не
  срабатывало: любой пользователь, узнав id задания, получал его статус и ключи
  приватных файлов с иллюстрациями ребёнка. Побочно: неавторизованный вызов
  запускал опрос провайдера, то есть тратил чужую квоту.
- **Исправление:** анонимное задание привязано к claim-cookie; доступ — только
  владельцу аккаунта или предъявителю токена. Авторизация теперь выполняется
  **до** обращения к провайдеру. Заодно исправлена сопутствующая поломка:
  анонимный посетитель раньше вообще не мог увидеть собственный предпросмотр,
  потому что маршрут файлов требовал сессию.
- **Проверка:** четыре теста в `tests/hardening.test.ts`, включая «задание без
  владельца и без токена недоступно никому».

### 3.3 Публичный server action рассылки писем — High

- **Файлы:** `src/app/actions/account-recovery.ts` → `src/lib/mail/verification.ts`
- **Суть:** `sendVerificationEmail(userId)` экспортировался из файла с
  `"use server"`. В App Router каждый такой экспорт — публичная точка входа. Она
  принимала произвольный `userId`, не проверяла ничего и не имела ограничения
  частоты: зная id, можно было бесконечно слать письма на чужой адрес и жечь
  квоту Resend.
- **Исправление:** функция перенесена в модуль `server-only`, недоступный
  снаружи. Вызывающие (регистрация и кнопка повторной отправки) сами проверяют
  права и лимиты.

### 3.4 Открытый редирект после входа — Medium

- **Файлы:** `src/app/(auth)/login/page.tsx`
- **Суть:** `callbackUrl` брался из строки запроса и передавался в
  `router.push()` без проверки. Ссылка `/login?callbackUrl=https://evil.example`
  уводила пользователя на чужой сайт **сразу после успешного входа** — момент,
  когда доверие максимально.
- **Исправление:** принимаются только внутренние пути; отвергаются абсолютные
  URL, протокол-относительные `//host` и вариант `/\host`, который браузер тоже
  читает как абсолютный.
- **Проверка:** таблица из девяти вариантов, все внешние формы → `/account`.

### 3.5 Обход ограничения частоты подделкой X-Forwarded-For — Medium

- **Файлы:** `src/lib/rate-limit.ts`
- **Суть:** `clientIp()` брал **левый** элемент `X-Forwarded-For`. Этот элемент
  задаёт сам клиент: прокси лишь дописывает справа. Меняя заголовок на каждом
  запросе, атакующий получал новый ключ лимита — то есть лимиты по IP на входе,
  регистрации и восстановлении пароля не работали вовсе.
- **Исправление:** сначала используются заголовки, которые ставит сама площадка
  (`cf-connecting-ip`, `x-vercel-forwarded-for`, `x-real-ip`), иначе берётся
  **правый** элемент; глубина настраивается `TRUSTED_PROXY_COUNT`.

### 3.6 Дублирование заказов при повторной отправке — Medium

- **Файлы:** `src/app/actions/orders.ts`, `src/app/(main)/checkout/CheckoutForm.tsx`,
  миграция `20260805000300_security_hardening`
- **Суть:** защита от двойного оформления была только на клиенте (блокировка
  кнопки). Повторный запрос после обрыва связи, двойной клик или повторная
  отправка формы создавали второй заказ.
- **Исправление:** ключ идемпотентности генерируется на клиенте один раз и
  проверяется на сервере; уникальный индекс разрешает гонку двух одновременных
  запросов — проигравший читает заказ победителя.

### 3.7 Отсутствовали заголовки безопасности — High

- **Файлы:** `next.config.ts`
- **Суть:** не было ни CSP, ни `X-Frame-Options`, ни `Referrer-Policy`, ни
  `Permissions-Policy`, ни HSTS. Админ-панель и оформление заказа можно было
  поместить в iframe на чужом сайте (кликджекинг).
- **Исправление:** CSP с `frame-ancestors 'none'`, `object-src 'none'`,
  `form-action 'self'`; `X-Frame-Options: DENY`; `Referrer-Policy`;
  `Permissions-Policy`; HSTS только в production; `no-store` для `/account`,
  `/admin` и `/api/uploads`; `X-Robots-Tag: noindex` на админке.
- **Ограничение честно:** `script-src` и `style-src` содержат `'unsafe-inline'`,
  потому что App Router встраивает inline-скрипты и стили. Причина и
  компенсирующая мера (никакой пользовательский ввод не рендерится как HTML, в
  коде нет `dangerouslySetInnerHTML`) описаны прямо в `next.config.ts`.

### 3.8 Ложное обещание об удалении фотографий — High (доверие)

- **Файлы:** `src/data/mock.ts`
- **Суть:** в FAQ было написано «Мы не передаём её третьим лицам и **удаляем
  после выполнения заказа**». Оба утверждения ложны: автоудаление не
  реализовано, а при включённой генерации фотография **передаётся** стороннему
  ИИ-провайдеру.
- **Исправление:** текст заменён на правдивый — фотография хранится в закрытом
  хранилище, её видят сотрудники и сервис генерации иллюстраций, удаление —
  по запросу.

### 3.9 Уязвимые зависимости — Critical

- **Файлы:** `package.json`
- **Суть:** `npm audit` показывал 8 уязвимостей, из них 2 критические:
  - **swiper 11.1.14** — прототипное загрязнение (critical). Пакет **не
    используется вообще**: галерея написана на CSS scroll-snap. Мёртвая
    зависимость с критической дырой.
  - **Next.js 15.3.2** — 31 уязвимость, включая **RCE в протоколе React
    flight** (critical), SSRF, отравление кеша, отказ в обслуживании.
- **Исправление:**
  - `swiper` удалён (0 использований в коде);
  - Next 15.3.2 → **15.5.22** — в пределах той же мажорной версии, поэтому без
    ломающих изменений; попутно закрылись postcss и sharp;
  - nodemailer 8 → 9 (обход `disableFileAccess` через опцию `raw`; мы её не
    используем, но версия всё равно обновлена).
- **Результат:** 8 уязвимостей (2 critical) → 3 (0 critical).
- **Проверка:** после обновления заново прошли typecheck, lint, сборка, 90
  тестов, живые запросы ко всем маршрутам, middleware и заголовки.

### Сопутствующие улучшения

- **Инвалидация сессий.** JWT нельзя отозвать. Добавлено поле
  `passwordChangedAt` и проверка в JWT-callback: смена пароля завершает все
  прочие сессии — то, чего человек и ждёт, меняя пароль после компрометации.
  Там же роль перечитывается из базы, поэтому снятый администратор теряет доступ
  немедленно.
- **Журнал действий администратора.** Таблица `admin_audit_log`: кто, что,
  когда — для смены статуса заказа и оплаты, публикации товара, удаления
  изображений, модерации отзывов, запуска генерации. Хранит идентификаторы и
  короткое описание, **не** персональные данные и не ключи файлов.
- **Ограничение частоты на смену пароля** — проверка текущего пароля была
  оракулом для подбора.
- **Изображения.** Ленивые изображения выбирали самый большой вариант из
  srcset: телефон качал 279 КБ там, где достаточно 93 КБ. Ограничены
  `deviceSizes`, включён AVIF (238 КБ в худшем случае). Улучшение реальное, но
  умеренное — исходники всего 1254 px.
- **Логи Auth.js** переведены в общий логгер: ротация `AUTH_SECRET` больше не
  заливает журнал ошибками уровня error.
- **`order-mail.ts`** перенесён из `src/app/actions/` в `src/lib/mail/` — он не
  был server action, но лежал среди них, что провоцировало ошибку.

## 5. Requires Real Credentials

**Ни одна интеграция ниже не проверялась с настоящим сервисом.** Код написан
целиком: запросы, разбор ответов, ошибки, таймауты, повторы. До первого
успешного обмена считать их работающими нельзя.

| Интеграция | Что готово | Что проверить с ключами |
|---|---|---|
| **Resend** | драйвер за общей абстракцией, журнал попыток в `email_messages`, проверка ключа в health-check | доходит ли письмо; подтверждён ли домен `MAIL_FROM`; не попадает ли в спам |
| **ЮKassa** | создание платежа с чеком, redirect, вебхук с перечиткой статуса из API, сверка суммы, идемпотентность, сверка зависших платежей | реальный платёж в тестовом магазине; доставка вебхука на боевой домен; формат чека под ваш налоговый режим |
| **Nano Banana** | постановка задания, опрос, скачивание, таймауты, отмена, лимит попыток, контрактный тест | **совпадают ли реальные поля API с ожидаемыми** — см. раздел 6 DEPLOYMENT-CHECKLIST |
| **Supabase Storage** | загрузка, чтение, удаление, подписанные ссылки | действительно ли приватный бакет закрыт; открывается ли подписанная ссылка и протухает ли за 5 минут |
| **S3 / R2** | то же через AWS SDK, path-style для не-AWS | то же, плюс права ключа |

**Особо про Nano Banana.** Публичной документации не было. Клиент написан по
типовой схеме submit → poll → download. Все предположения изолированы в
`src/lib/generation/nano-banana.ts` и зафиксированы контрактным тестом

| Двухфакторная аутентификация | вне объёма |
| Rate limiting на Redis | счётчики в базе; при высокой нагрузке меняется одна функция |
| Экспорт метрик (Prometheus/OTel) | есть структурные логи и `/api/health` |

### Технический бэклог (для планирования)

1. Удаление аккаунта покупателем — с корректной судьбой заказов (заказы
   сохраняются, персональные данные обезличиваются).
2. Экспорт персональных данных по запросу.
3. Политика хранения: срок жизни фотографий и автоматическая очистка.
4. Автоудаление фотографий после печати — **только после п. 3**.
5. Возврат платежа через API ЮKassa.
6. Процедура удаления по запросу силами администратора (сейчас вручную в базе).
7. Уборка «осиротевших» файлов в хранилище.

**Юридические тексты — заглушки.** `/privacy`, `/personal-data-policy`,
`/terms`, `/promotion-rules` содержат структуру и заголовки разделов, но не
готовый юридический текст. Их обязан написать или проверить юрист до запуска.
Ни на одной странице не утверждается соответствие конкретному закону.

## 8. Security Findings

### Устранено в этом аудите

| Находка | Уровень |
|---|---|
| IDOR на странице подтверждения заказа (утечка email, суммы, номера) | Critical |
| Задания генерации без владельца читал любой пользователь | High |
| Публичный server action рассылки писем без авторизации и лимита | High |
| Отсутствие CSP и заголовков безопасности (кликджекинг) | High |
| Ложное обещание об удалении фотографий и о непередаче третьим лицам | High |
| Открытый редирект после входа | Medium |
| Обход лимитов подделкой X-Forwarded-For | Medium |
| Дублирование заказов при повторной отправке | Medium |
| Сессии переживали смену пароля | Medium |
| Отсутствие журнала действий администратора | Medium |
| Смена пароля без ограничения частоты (оракул подбора) | Low |

### Проверено и признано корректным

- Цены и итоги считаются на сервере; данные браузера не используются.
- Роль администратора перечитывается из базы при каждой мутации, а не берётся
  из токена; middleware — только первая линия.
- Загрузки проверяются по сигнатуре файла, а не по заявленному MIME.
- Ключи хранилища — UUID; обход каталога невозможен.
- Приватные файлы отдаются подписанной ссылкой на 5 минут после проверки прав.
- SQL-инъекция: весь доступ через Prisma; сырые запросы параметризованы или
  содержат только константы.
- XSS: пользовательский ввод нигде не рендерится как HTML;
  `dangerouslySetInnerHTML` в коде отсутствует.
- SSRF: единственный исходящий запрос по внешнему URL — скачивание результата
  генерации, и он ограничен размером, таймаутом и списком форматов.
- Вебхук не доверяет телу запроса: статус перечитывается из API провайдера.

### Принятые остаточные риски

| Риск | Почему принят |
|---|---|
| `'unsafe-inline'` в `script-src`/`style-src` | требуется App Router; nonce потребовал бы middleware на каждый ответ и сделал бы динамическими все страницы. Компенсация: React экранирует весь ввод, `dangerouslySetInnerHTML` не используется |
| Лимиты частоты в PostgreSQL | при высокой нагрузке строки станут «горячими». Заменяется одной функцией |
| Локальный PostgreSQL для разработки (PGlite) рвёт соединение на нарушении ограничения | влияет только на тесты; они проверяют факт отказа записи, а не код ошибки Prisma |
| Ленивые изображения выбирают крупный вариант srcset | ограничено `deviceSizes` и AVIF; полное решение потребовало бы отказаться от ленивой загрузки в карусели |
| Нет защиты от перебора по всему диапазону IPv6-подсети | лимиты дополнительно ключуются на адрес аккаунта |
| **3 уязвимости high, закрываемые только переходом на Next 16** | разобраны ниже |

### Остаточные уязвимости зависимостей

После обновлений остаются три, и все три закрываются только мажорным переходом
на Next 16. Делать его за день до запуска — больший риск, чем сами уязвимости.
Оценка по каждой:

| Пакет | Почему принято |
|---|---|
| **postcss** (high) | Все четыре CVE — про `sourceMappingURL` в CSS и вывод stringify. postcss работает **только на этапе сборки**, обрабатывая наш собственный CSS. В production он не запускается, и никакой чужой CSS через него не проходит. Не эксплуатируется. |
| **sharp / libvips** (high) | sharp используется оптимизатором изображений Next. Проверено, какие изображения до него доходят: фотографии детей и сгенерированные иллюстрации отдаются с `unoptimized` и **не попадают в sharp**; удалённые хосты запрещены (`remotePatterns: []`). Остаётся один путь — артворк каталога, загруженный **администратором**. То есть для эксплуатации нужен доступ администратора, у которого и без того есть все права. |
| **next** (high, агрегат) | 15.5.22 — последняя в ветке 15.x. Критический RCE и SSRF уже закрыты; остаток требует Next 16. |

**Рекомендация:** запланировать переход на Next 16 в первые недели после
запуска, отдельной задачей, с полным прогоном тестов — не совмещая с релизом.

## 10. Launch Recommendation

### **LIMITED BETA AFTER CONFIGURATION**

Код готов. Разворачивайте, подключайте внешние сервисы и пройдите
`LIVE-VERIFICATION-CHECKLIST.md` целиком.

**Почему не публичный запуск сразу:** ни одна внешняя интеграция не
подтверждена живым обменом. Пока Resend, ЮKassa и хранилище не проверены на
боевом домене, обещать покупателям приём заказов нельзя.

**Порядок:**

1. Развернуть, подключить базу, хранилище и Resend.
2. Пройти части 1–3 живого чеклиста. Все 🛑 обязаны пройти.
3. Открыть магазин ограниченному кругу (знакомым, первым покупателям),
   с оплатой при подтверждении либо после платежа на минимальную сумму в
   ЮKassa.
4. Публичный запуск — после того, как хотя бы один настоящий заказ прошёл весь
   путь: оплата, письма, смена статусов, доставка.

**Nano Banana включать последним**, уже после сверки с настоящей документацией.
Пока он выключен, сайт честно пишет, что иллюстрации готовятся вручную, и
магазин полностью работоспособен.

**Не обещайте публично**, пока это не реализовано и не проверено:
автоматическое удаление фотографий, автоматический возврат средств,
самостоятельное удаление аккаунта, работу ИИ-генерации, соответствие
конкретному закону.
